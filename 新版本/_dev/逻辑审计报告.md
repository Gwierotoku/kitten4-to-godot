# 循环 / warp 逻辑审计报告

> 审计对象：`新版本` 转换器的**控制流（循环）与 warp** 实现
> 审计方式：**只读**静态审计 —— 读转换器（`lib/k4/emit.js`、`methodtable.js`）、运行时库（`runtime/全局/*.gd`）、**生成产物**（`_out/**`），并对照 K4 Ultra 打包产物里的解释器源码（`K4-ULTRA-main/resources/app/build/kitten.822d814413fb10654fde.js`）
> 本次审计**没有修改任何被审计文件**（唯一的写操作就是本报告）
> 结论：让出/warp 的主干是对的；发现 **1 个已在真实工程中命中的缺陷**（P1）、**6 个 P2**、**6 个 P3/设计风险**

---

## 0. 结论摘要

| 级别 | 含义 | 条数 | 是否有真实案例命中 |
|:---|:---|---:|:---|
| **P1** | 缺陷已发生，影响正确性或产出物 | 1 | ✅ 命中（`子弹/当满足条件_2.gd`、贴图副本条件帽子） |
| **P2** | 有明确缺陷，但当前用例恰好不触发 / 影响有界 | 6 | 未命中或影响可忽略 |
| **P3** | 设计风险 / 契约破损 / 文档与实现不一致 | 4 | — |

**最值得立刻修的三条**（详见 §2）：

1. **`_条件()` 每帧新建 `ctx`，且被条件表达式真实引用**（B1）→ 每帧每条件帽子分配一个对象，且这个 ctx 不属于任何协程、永不被取消。
2. **`帽子_条件._ready()` 完全覆写基类 `_ready()`**（B2）→ 基类契约 C 里承诺的 `_周期任务()` 永远不会被调用（目前无子类覆写，属"契约已死"的定时炸弹）。
3. **`_上下文()` 的兜底分支会把帽子永久卡死**（B5）→ 一旦命中，那个帽子从此再也无法被事件触发。

另有一条**关于验证有效性的重要提醒**（B10）：`转换并验证.cmd` 里的 "0 error / 0 warning" **测的是运行时 stderr 行数为 0**，它**不检测 GDScript 的编译期警告**（如 `UNUSED_VARIABLE`）。所以 README/汇报里"0 warning"这个说法比实际承诺更强，验证手段覆盖不到它。

## 1. 循环逻辑全景（含完整让出判定链）

### 1.1 一图看全：谁在让出、谁不让出

```
┌──────────────────────────── 帽子（= K4 的一个事件线程） ────────────────────────────┐
│ 帽子基类._ready()                                                                   │
│   └─ await physics_frame            ← 等父节点(角色)_ready 完成                       │
│       └─ 启动()  【同步】                                                            │
│            └─ _点火()  【同步】                                                      │
│                 ├─ _ctx = new WarpCtx()      ← ★本次运行的唯一 ctx★                  │
│                 ├─ _运行中 = true                                                    │
│                 └─ call("_跑主体")            ← 点火，丢弃协程句柄 = 后台协程          │
│                      └─ await call("_积木主体")   ← 生成代码，长这样：                 │
│                                                                                     │
│                          var ctx = _上下文()      ← 拿到 _点火 里那个 ctx              │
│                          while true:              ← 「重复执行」                      │
│                              ...积木...                                             │
│                              await 角色.一步(ctx)  ← ★唯一的让出点（生成器自动补）★     │
│                                                                                     │
│                      └─ 跑完后 _结束运行()（仅当 _ctx 仍是本轮）                       │
└─────────────────────────────────────────────────────────────────────────────────────┘
```

### 1.2 `一步()` 的完整让出判定链（[角色基类.gd:185-201](新版本/runtime/全局/角色基类.gd)）

```
一步(ctx)
  │
  ├─ ctx._已取消 == true ─────────────────────────► return（立即返回，不让出）
  │                                                  ↑ 注意：不是 break，见 B6
  │
  ├─ ctx.depth == 0（不在 warp 里）─┐
  │                                  │
  ├─ ctx.depth > 0（在 warp 里）─────┤
  │      │                           │
  │      ├─ 物理帧号 != 缓存帧号 → 重置 本帧起点 = now
  │      │
  │      ├─ 本帧已用 = now - 本帧起点
  │      │
  │      └─ 四个条件【全满足】→ iters += 1; return（不让出）
  │           ① ctx.iters < 10000              （照抄 K4）
  │           ② now - ctx.started < 100ms      （照抄 K4）
  │           ③ 本帧已用 < 8ms                  （★Godot 特有补丁★）
  │           ④（隐含）未被取消
  │
  └────────────────────────────────► ctx.iters = 0; ctx.started = now
                                     await get_tree().physics_frame   ← 真正让出一帧
```

四个条件的含义：

| 条件 | 来源 | 作用 |
|:---|:---|:---|
| `depth > 0` | K4 `is_inside_warp()` | 判断"我是不是在 warp 里" |
| `iters < 10000` | K4 `max_warp_iterations_per_interpreter_step` | 防死循环（迭代粒度） |
| `- started < 100ms` | K4 `warp_interpreter_millisecond_time_limit` | 防死循环（时间粒度） |
| `本帧已用 < 8ms` | **本项目新增** | 防"几十个角色并行 warp"叠加成几秒一帧 |

### 1.3 嵌套 warp 的协程时序

K4 的 warp 状态沿**调用栈**传播（`is_inside_warp()` 里那三项 `is_warped || current_frame.is_warped || n_warp_parents > 0`）。移植版用**同一个 `ctx` 对象在协程间传递**来表达这件事：

```
帽子协程                          角色.进入warp(ctx)            一步(ctx) 判定
─────────────────────────────────────────────────────────────────────────────
var ctx = _上下文()                depth=0
进入warp(ctx)                      depth 0→1，重置 iters/started
  while true:                                                    depth=1 → warp 快路径
    进入warp(ctx)   ← 嵌套        depth 1→2，★不重置★（见 [角色基类.gd:164](新版本/runtime/全局/角色基类.gd)）
      await 一步(ctx)                                            depth=2 → 共享外层 100ms
    退出warp(ctx)                  depth 2→1
    await 一步(ctx)                                            depth=1 → 仍在 warp 里
退出warp(ctx)                      depth 1→0
await 一步(ctx)                                                depth=0 → 真让出一帧
```

关键设计：**`ctx` 必须随协程传递**。因为 Godot 里几十个角色的 warp 段是**并行协程**，而 K4 是单线程解释器——把 `depth` 存成节点成员变量就会互相污染。这是 `WarpCtx` 内层类存在的唯一理由，代码注释里也写了。

### 1.4 循环 → 生成代码对照

| K4 积木 | 生成 | 让出点 |
|:---|:---|:---|
| 重复执行 | `while true:` | 体末尾 `await 一步(ctx)` |
| 重复执行 N 次 | `for _k4iN in range(角色.转整数(...)):` | 体末尾 `await 一步(ctx)` |
| 重复执行直到 条件 | `while not 条件:` | 体末尾 `await 一步(ctx)` |
| 等待直到 条件 | `while not 条件: await 一步(ctx)`（内联展开） | 每轮 |
| warp | `进入warp(ctx)` / 体 / `退出warp(ctx)`，**体本身不加让出点** | 无 |
| 等待 N 秒 | `await 角色.等待_秒(ctx, N)`，内部 `while 未到点: await 一步(ctx)` | 每帧 |

> ⚠ **warp 体不自动加让出点**正是 warp 的意义所在；但如果 warp 体里恰好**没有**循环，`进入warp` / `退出warp` 之间根本没有 `一步()` 调用——这意味着 **warp 的 10000 次 / 100ms 预算在"体里无循环"时完全不起作用**（无害，因为无循环就不可能死循环）。

## 2. 缺陷清单（按级别）

### P1

#### B1 — `_条件()` 每帧新建 `ctx`，而且真的被引用（性能 + 取消语义）

**位置**：[emit.js:1333-1346](新版本/lib/k4/emit.js)（条件帽子的 `_条件()` 生成）

生成器给 `_条件()` 生成了这样一行：

```gdscript
func _条件() -> bool:
    var ctx: 角色基类.WarpCtx = 角色.新建上下文()
    return ...
```

我原本以为这只是"未使用变量"。**查产物后发现：`ctx` 在真实工程里真的会被引用**——

[空白作品/背景/子弹/当满足条件_2.gd:6](新版本/_out/空白作品/背景/子弹/当满足条件_2.gd)：

```gdscript
func _条件() -> bool:
    var ctx: 角色基类.WarpCtx = 角色.新建上下文()
    return (... 角色.为真(角色.找("背景").按下按键(ctx, "J")) ...)
                                   ^^^^^^^^^^^^^^^^^^^^^^^ 传的是上面那行新建的 ctx
```

同样的形态还在 `<角色>_副本.gd`（贴图副本条件帽子）里出现。

后果：

1. **每帧每个条件帽子分配一个 `WarpCtx`**。`_条件()` 由 [`帽子_条件._process`](新版本/runtime/全局/帽子_条件.gd) 每帧调用；条件帽子的数量与角色数同阶（本工程 37 角色量级），于是每帧几十次对象分配。条件帽子越多越明显。
2. **这个 `ctx` 不属于任何协程，永远不会被 `_已取消`**。它被传进跨角色调用（`角色.找("背景").按下按键(ctx, ...)`），如果那条链路上有 `一步(ctx)` 或 `等待_秒(ctx, ...)`，就会拿一个"无主 ctx"——`_取消` 永远为 false，`depth` 永远是 0。也就是说：**经由条件表达式触发的等待，不会被绿旗重启/停止脚本打断**（对比：`_积木主体()` 用的是 `_上下文()`，是正确的）。
3. 与 [帽子基类.gd【契约 B】](新版本/runtime/全局/帽子基类.gd) 的明文约定直接冲突——那条注释写着"★必须用 `_上下文()`，不能用 `角色.新建上下文()`★"。

**修复方向**（不改语义的最小改法）：让 `_条件()` 也走 `_上下文()`。注意 `_上下文()` 会顺带把 `_运行中 = true`（见 [帽子基类.gd:151-155](新版本/runtime/全局/帽子基类.gd)），对轮询型帽子不合适——所以更干净的是**给条件帽子单独一个长期 ctx**（例如在 `帽子_条件._ready()` 里建一个 `_轮询ctx`，`_条件()` 里用 `var ctx := _轮询ctx`），它的 `depth` 恒为 0、`_已取消` 由基类统一管。

### P2

#### B2 — `帽子_条件._ready()` 覆写基类 `_ready()`，基类契约 C 已死

**位置**：[帽子_条件.gd:29-33](新版本/runtime/全局/帽子_条件.gd) vs [帽子基类.gd:73-78](新版本/runtime/全局/帽子基类.gd)

基类 `_ready()` 做三件事：`_已启动 = true`、**`_触发条件满足()` → 启动()**、**`_周期任务()`**。

`帽子_条件` 把整个 `_ready()` 重写了，只做了 `_已启动 = true` + `set_process(true)`：

- `_触发条件满足()` 没调 → 对条件帽子无害（它本来就该等边沿触发），但**语义上依赖了"基类默认返回 false"这个安全网**，一旦有人给条件帽子覆写 `_触发条件满足()` 返回 true，行为会静默失效。
- **`_周期任务()` 没调** → [基类契约 C](新版本/runtime/全局/帽子基类.gd) 明文写着"条件/计时器/响度/背景切换这些轮询型帽子覆写 `_周期任务()` 做边沿检测"。**目前全工程无任何子类覆写 `_周期任务()`**（我 grep 过 `runtime/`，只有基类的定义和调用两处），所以这条契约事实上从未被使用，也就没暴露成 bug。但只要有人照着契约去覆写，就会**静默不生效**。

`帽子_背景切换` 和 `帽子_广播`、`帽子_点击`、`帽子_屏幕切换` 也都各自重写了 `_ready()`（同样不调 `_周期任务()`），但它们的 `_触发条件`/`_周期任务` 语义不同，属于设计选择。

**修复方向**：把条件帽子的 `_ready()` 改成覆写 `_触发条件满足() -> false` 之外的钩子，或者让基类把 `_周期任务()` 拆成独立的、不被覆写的调用点（例如基类用 `_ready()` → `call("_周期任务")`，子类只覆写 `_周期任务` 而不覆写 `_ready`）。最省事的做法：**在 `帽子_条件._ready()` 末尾补一行 `_周期任务()`**，把契约救回来。

#### B3 — `删除自己()` 之后协程的"空转段"：会多执行几轮积木体

**位置**：[角色基类.gd:565-569](新版本/runtime/全局/角色基类.gd) + [角色自带积木.gd:216-219](新版本/_out/空白作品/全局/角色自带积木.gd)

`删除自己()` → `k4_alive = false; queue_free()`。而"停止"要等到下一次 `一步()` 才生效：

```gdscript
func 一步(_ctx):
    if not k4_alive:
        _ctx._已取消 = true          # 标记，但——
    await super.一步(_ctx)            # ← 仍然让出一帧才返回
```

所以删除后**当前这一轮的剩余代码会全部跑完**（如果剩余代码里没有 `一步()`），直到下一个 `一步()`。在 `for` / `while` 体很长、或嵌套较深时，这是"死后还在改数据"的窗口。K4 的原语义是 `dispose` 立刻终结脚本。

**实测影响**：`等待_秒` 内部每次 `await 一步()` 后会检查 `if not k4_alive or ctx._已取消: return`，所以等待途中的删除是及时的；纯同步长代码块才会出现窗口。**评估为 P2**（正确性风险，非崩溃）。

#### B4 — 广播帽子的"等待跑完"依赖 `_监听上下文`，且预调用先于 `emit_signal`

**位置**：[广播总线.gd:130-149](新版本/runtime/全局/广播总线.gd)、[帽子_广播.gd:36-37](新版本/runtime/全局/帽子_广播.gd)

```gdscript
func 发信号并等待(_名: String) -> void:
    var 可等 := _运行者(_名)      # ← ① 这里就 call("_监听上下文")，等于**先启动了一遍**
    emit_signal(规范)             # ← ② 这里又广播一遍 → 监听者被调用两次
    for 项 in 可等:
        await 项                  # ← ③ 等的其实是 ① 里那个协程句柄
```

`_运行者` 里 `目标.call("_监听上下文")` 会**立即执行** `_监听上下文` 的函数体到第一个 `await`——也就是立即执行 `启动()`（因为 [帽子_广播.gd:37](新版本/runtime/全局/帽子_广播.gd) 写的是 `await 启动()`，而 `启动()` 是**同步函数**）。于是：

- ① 启动了积木体（`_运行中 = true`）；
- ② `emit_signal` 再次触发 `_监听上下文` → `启动()` → 被 `if _运行中: return` 挡掉；
- ③ `await 项` 等的是 ① 的协程。

**功能上成立**（正是靠 ② 被去重才没跑两遍），但这是**靠"事件型帽子不重入"这条副作用凑出来的**，非常脆：任何让 `启动()` 变成可重入的改动（或让 `_运行中` 提前落回 false）都会立刻变成"广播体跑两遍"。

另外 [帽子_广播.gd:37](新版本/runtime/全局/帽子_广播.gd) 的 `await 启动()` —— `启动()` 是同步函数，这里的 `await` 在语义上是多余的（注释却写着"启动() 是协程"，与 `帽子基类.gd` 自己的【契约 A】"启动/重启一律是同步函数"矛盾）。它目前**不产生 warning**（分析器无法跨函数静态判定 `启动` 是否协程），但注释是错的，会误导后续维护。

#### B5 — `_上下文()` 的兜底分支会把帽子永久卡死

**位置**：[帽子基类.gd:151-155](新版本/runtime/全局/帽子基类.gd)

```gdscript
func _上下文() -> 角色基类.WarpCtx:
    if _ctx == null:
        _ctx = 角色基类.WarpCtx.new()
        _运行中 = true           # ← 副作用：把帽子标成"正在运行"
    return _ctx
```

目前所有生成代码都在 `_点火()` 之后才调 `_上下文()`，所以这条分支从不命中。但它是"从外部进入积木体"的隐式入口，一旦命中就会**跳过 `_点火()`**（不置 `_已启动` 检查、不建信号等待）却把 `_运行中` 置真 —— 后果是那个帽子从此**再也无法由事件触发**（`启动()` 被 `_运行中` 挡死），而 `_跑完` 也永远不会发出（`_跑主体` 没跑）。这是"设计上不该存在"的分支，建议改成 `push_warning` + 返回临时 ctx，或者直接删掉兜底。

#### B6 — `一步()` 在"已取消"时 return 而不是让出：取消后不释放帧

**位置**：[角色基类.gd:186-187](新版本/runtime/全局/角色基类.gd)

```gdscript
func 一步(_ctx: WarpCtx) -> void:
    if _ctx._已取消:
        return                    # ← 直接返回，一次 await 都没有
```

被取消的协程在**没有其它 await 源**的循环里会**同帧空转**（每次 `一步()` 立即返回），只有循环体里恰好有别的 `await`（`等待_秒`/`广播并等待`/自定义积木协程）才会真正挂起。最坏情况是 `while true: ... await 一步(ctx)` 这种纯同步体——它会在**同一帧内无限循环**下去，永不退出。

我检查了实际生成代码：取消后能"同帧无限跑"的形态（纯同步循环体 + warp 内循环）确实存在（例如 `空白作品/背景/敌人/当克隆体启动时_1.gd` 里多处 `进入warp` + `for` + `await 一步`），但因为每条路径最终都有 `await`（至少 `await super.一步` 那一行在**未取消**时让出；取消那一刻之后才会变成纯空转），实际堆栈里**不会**出现"永不返回"。

不过这是**脆弱的**：正确性依赖"取消路径上恰好存在别的 await"，而不是设计保证。建议改成"取消时也 `await` 一帧再 return"（代价是多一帧延迟退出，收益是彻底消除同帧空转的可能）。

### P3 / 契约与文档

#### B7 — `等待直到(ctx, 布尔值)` 退化成"等一帧就当满足"

**位置**：[角色_自带积木.gd:311-320](新版本/_out/空白作品/全局/角色自带积木.gd)

`等待直到` 在生成器侧已被内联展开成 `while not 条件:`，所以这个运行时方法**基本走不到**。但它若被走到且传进来的是**已求值的布尔**（不是 Callable），会 `await 一步(ctx)` 后直接返回——即"无条件立即满足"。代码注释已诚实标注了这个限制。

#### B8 — 条件帽子的"运行中不重入"可能偏离 K4

**位置**：[帽子基类.gd:115-120](新版本/runtime/全局/帽子基类.gd) + [帽子_条件.gd:35-41](新版本/runtime/全局/帽子_条件.gd)

`启动()` 里有 `if _运行中: return`。对**事件型**帽子（按键/点击/广播）这是对的（K4 同一脚本不重入）。但**条件帽子**在 K4 里是"条件为真 → 触发"的堆栈事件：如果条件帽子的积木体带一个长循环（`当满足条件` 里套 `重复执行直到…`），则积木体运行期间条件再变真也不会再触发。这可能是对的（防止雪崩），也可能是偏离。**需要你确认 K4 的实际表现**。

#### B9 — `K4Bus.发信号并等待` 存在互等死锁面

**位置**：[广播总线.gd:130-136](新版本/runtime/全局/广播总线.gd)

A 广播 X 并等待 → X 的监听者里若有 B，B 的积木体又"广播 Y 并等待"，而 Y 的监听者包含 A —— 则两个协程互等。K4 里是否也会死锁需实测。低频，标注为风险。

#### B10 — 验证方案的 "0 warning" 覆盖不到编译期警告（重要）

**位置**：[huanzhuang.ps1:88-103](新版本/huanzhuang.ps1)

```powershell
if ($line -match 'ERROR|SCRIPT ERROR|WARNING') { [void]$bad.Add($line) }   # 只扫 run.err
```

验证器数的是**运行时 stderr 里的行**。GDScript 的**编译期警告**（`UNUSED_VARIABLE`、`SHADOWED_VARIABLE`、`REDUNDANT_AWAIT` 等）在运行工程时是否被打印到 stderr，取决于引擎实现，**不在这个脚本的检查设计里**。而 README / 技术路线汇报把结论写成"0 error / 0 warning"，读者会理解成"没有编译警告"。**建议把措辞改成"运行期 stderr 0 行 + 全量解析 0 失败"**，或者补一步真正的编译警告检查。

顺带：`parse-check` 那一步（[huanzhuang.ps1:58-81](新版本/huanzhuang.ps1)）只匹配 `Parse Error|Compile Error|Failed to load script|Invalid scene|...`，**同样不含 WARNING**。所以 B1 里那种"`_条件()` 里 `var ctx` 被使用但每帧重建"的问题，以及潜在的 `UNUSED_VARIABLE`，验证链路是**看不见**的。

#### B11 — `_条件()` 直接在 `-> bool` 里内联 `await` 调用的隐患（与 B1 同源）

**位置**：[emit.js:1333-1346](新版本/lib/k4/emit.js)

若某个 `当满足条件` 的**条件表达式**里含 await 类取值积木（`询问并等待` 等），生成器会产出 `return await 角色.询问并等待(ctx, ...)` —— 位于 `func _条件() -> bool` 里。

- 若 `ctx` 缺失 → `Identifier "ctx" not declared`（B1 的变体；当前 6 个真实条件表达式里只有 1 个引用 ctx，未触发）；
- 若 `ctx` 存在 → 该函数变成协程，`await` 让出后 `_process` 里 `if 本帧 and not _上次为真` 拿到的返回值可能不是 bool，`条件函数.call()` 的 `bool()` 转换会静默把 null 当 false。

当前 4 个用例未命中。**建议**：`_条件()` 里如果表达式含 await，应显式报错或降级成"不支持"，而不是生成可能出错的代码。

## 4. 复核过、确认**不是** bug 的项（避免重复怀疑）

### 4.1 关于"全帧 8ms 预算"是否真的共享（值得单独记录）

我一度怀疑"每个角色进入 warp 都重置预算"会让"全帧共享 8ms"退化成"N 个角色各得 8ms"。逐行复核后**这个怀疑不成立**：

```gdscript
func 进入warp(_ctx):
    if _ctx.depth == 0:
        _ctx.iters = 0                          # 只动 ctx 自己的字段
        _ctx.started = Time.get_ticks_msec()     # 只动 ctx 自己的字段
    _ctx.depth += 1
```

`进入warp` 触碰的只有**当前协程持有的 `ctx`**，完全不碰帧级静态变量。而帧级起点只在一处更新：

```gdscript
if _warp帧号 != 本帧:            # 本帧第一次调 一步() 才会进这里
    _warp帧号 = 本帧
    _warp帧起点 = Time.get_ticks_msec()
```

于是同一帧内：角色 A 把 `本帧已用` 跑到接近 8ms 后让出，角色 B 再进 `一步()` 时**帧号没变 → 不重置起点 → 拿到的仍是同一个起点**，`本帧已用` 继续累加 → B 也随之让出。**共享是成立的。**

唯一残留的现实限制：预算的检查粒度是"一次迭代结束后"，所以单次迭代本身就超过 8ms（例如一次 `文本分割` 处理 8MB 谱面）时会超支跑完这一次迭代才让出。这与 K4 的 100ms 上限共同兜底，**不可避免也无需修**。

### 4.2 其余复核项

| 疑点 | 结论 | 依据 |
|:---|:---|:---|
| "全帧 8ms 预算"没生效 | **成立**，是共享的 | `_warp帧起点` 只在"帧号变化"时更新，同帧所有角色读同一个起点（详见 §4.1） |
| `进入warp()` 重置预算 → 每角色各得 8ms | 不成立 | `进入warp` 只动 `ctx` 自己的字段，不碰帧级静态变量（§4.1） |
| 首帧 `_warp帧起点 = 0` / 帧号 0 撞车 | 只影响首帧少数角色多让一帧，自愈 | 判负 → 重置起点；且 `_warp帧号` 初值 `-1`，首次必然进初始化分支 |
| 切屏后 `static _warp帧号` 过期 | 不会 | `Engine.get_physics_frames()` 是引擎级单调计数，不随场景重置 |
| `帽子_屏幕切换._在屏幕就绪()` 等了一帧却没用返回值 | 不是 bug | `K4Canvas.画布` 是属性读取，`await` 之后再读会重新取值，正是意图 |
| 绿旗重启后旧协程把 `_运行中` 抹掉 | 已防住 | [`_跑主体`](新版本/runtime/全局/帽子基类.gd) 用 `本轮` 比对 |
| `wait_until` 会不会死等到超时 | 生成器已内联成 `while not 条件` | [emit.js:1098-1103](新版本/lib/k4/emit.js) |
| 嵌套 warp 无限续期预算 | 已防住（只在 `depth == 0` 重置） | [角色基类.gd:164](新版本/runtime/全局/角色基类.gd) |
| `重复执行` 在 warp 里会不会不让出 | 会不让出，这正是 warp 语义 | 生成的 `while true` 体末尾 `await 一步(ctx)` 在 `depth > 0` 时走快路径 |
| `停止全部` 用 `paused` 卡死 | 已避开，走 `_停整棵树` 标记 | [角色自带积木.gd:258-289](新版本/_out/空白作品/全局/角色自带积木.gd) |
| warp 体里没有循环时预算不起作用 | 无害 | 无循环就不可能死循环 |
